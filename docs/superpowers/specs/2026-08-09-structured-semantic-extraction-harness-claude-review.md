# Claude 对结构化语义抽取 Harness 的独立审查

**日期：** 2026-08-09  
**审查模型：** `claude-opus-4-8`  
**执行方式：** 本机 Claude Code，只读文件，禁用网络和写入  
**耗时：** 90.137 秒  
**用量：** 输入 7,989 token，输出 3,970 token  
**Claude 结论：** 方向正确，但当前版本不建议批准，需修订后复审

## Claude 提出的阻塞问题

1. 字段级修复没有定义跨字段、跨主体和报告期的一致性边界。
2. Profile 只有“暂停”描述，没有暂停、验证、恢复和回滚状态机。
3. 150 篇不足以同时证明 15 个事件类型的生产质量。
4. 表格 IR 没有完整覆盖多层表头、跨页续表、脚注、单位冲突和歧义。
5. 10 篇原子批次与 150 篇盲测之间的验收关系没有定义。

## Claude 提出的重要问题

1. API 与 Coding Plan 的“无差别执行”表述过强；两者推理预算、错误和重试
   模式不同。
2. 离线 claim 过期、迟到结果、重复 Provider 结果和 task token 生命周期
   没有闭环。
3. 复杂度分类的实际判定边界没有落到合同。
4. Planner 失败后的 quarantine、降级和失败率统计未定义。
5. 没有区分“证据包漏节点”和“LLM 引错节点”，错误归因可能错误。
6. 两阶段数据流在图与文字中仍可能产生实现歧义。

## Claude 认为可能过度设计的部分

- 所有复杂文档都增加 LLM Planner，收益尚未被证明。
- 只修一个字段、最多一次的中间方案可能同时增加状态和一致性风险。
- 为离线 Coding Plan 设计动态 claim/lease，首期实现复杂。

## Codex 对审查意见的判断

### 接受

- 完善表格 IR，而不是继续让 Prompt 猜表头关系。
- 把修复单位从单字段提升为完整事件候选，并重新运行整体一致性校验。
- 增加 task/profile 状态机、漂移恢复、积压重放和 lineage 回滚流程。
- 明确 10 篇开发 canary、预验收集和生产验收集的层级关系。
- 区分 IR/证据包缺陷、Provider 输出缺陷和 Compiler 缺陷。

### 部分接受

- 150 篇适合作为预验收，不足以作为 15 个事件族的最终生产证明。生产门应
  扩大到至少 600 篇：每个事件族至少 30 篇，另保留 no-event 和困难样本。
- API 与 Coding Plan 可以共享语义合同和冻结证据，但不能承诺推理过程、
  延迟和错误行为相同。文档应改为“合同等价”，不是“执行无差别”。
- 两阶段能力仍有价值，但应改为默认确定性检索加单阶段抽取；只有证据窗口
  超预算或多事件歧义时才调用 LLM Planner。

### 不接受

- 不接受首期只做 API、以后再支持 Coding Plan。双执行模式是明确需求，应
  首期实现，但可以取消动态 lease：任务创建时固定分配执行通道，切换通道
  时创建新的、可追溯任务。
- 不接受把完整长文或完整大表无条件交给单次 LLM。Document IR 的目的之一
  就是提供可验证、受预算约束的证据窗口。

## 建议的最小修订

1. 扩展表格 IR：层级 header path、跨页 continuation、脚注关系、单位优先级、
   歧义标记和 parser provenance。
2. 删除字段级原地修改，改成“完整事件候选重新抽取一次 + 全事件校验”。
3. 增加 task 与 profile 状态机，以及暂停、修复、重放、恢复和回滚规则。
4. 将动态 claim/lease 简化为 job 创建时固定 `executor_mode`；迟到或重复结果
   只作为独立审计 run，不自动晋级。
5. 将评估拆成 150 篇预验收和至少 600 篇生产验收，两个阶段均使用冻结合同。
6. 默认单阶段抽取；只有结构复杂度和证据预算触发时才使用 LLM Planner。
